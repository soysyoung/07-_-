# 실습 08 프로젝트 이해 노트

## 1. 이 프로젝트를 한 문장으로 설명하면

실습 07에서 완성한 **Multi Agent 실행 로그 EDA 프로젝트의 제출물**이 요구 조건을 만족하는지 자동으로 검증하고, 자동 검사가 판단하지 못하는 보고서 품질과 개인 기여 내용까지 제출 준비하는 평가 프로젝트이다.

이 실습에서는 새로운 데이터를 분석하거나 새 Git 저장소를 만드는 것이 아니다. 같은 난이도의 실습 07 프로젝트를 먼저 실행해 결과물을 만든 다음, 실습 08의 검증 코드로 그 결과가 올바른지 검사한다.

```text
실습 07 프로젝트 실행 및 결과 생성
→ 실습 08 검증 함수 완성
→ 자동 검사 실행
→ 보고서와 테스트 기록 보완
→ Git 이력과 개인 기여 확인
→ 최종 제출
```

## 2. 실습 07과 실습 08의 관계

| 구분 | 실습 07 | 실습 08 |
|---|---|---|
| 핵심 목적 | 데이터를 정제·집계하고 그래프와 결과 파일 생성 | 생성된 결과와 제출 구성을 검증 |
| 주요 작업 | EDA 파이프라인 구현 | 검증 로직 구현 및 제출 점검 |
| 주요 입력 | `data/agent_runs.csv` 등 | 실습 07 프로젝트 폴더 전체 |
| 주요 출력 | CSV, JSON, PNG, 분석 보고서 | 자동 오류 목록과 수동 검토 항목 |
| 주의점 | 원본 데이터를 변경하지 않음 | 정답 결과나 검사 기준을 수정하지 않음 |

기본필수 실습 08이 검사할 실제 프로젝트 위치는 다음과 같다.

```text
ex07_project/01_기본필수/day4_eda
```

실습 08 폴더 자체를 분석 결과 제출 폴더로 사용하는 것이 아니다.

## 4. 직접 구현할 핵심 부분

기본필수 단계에서 직접 완성할 핵심은 `validate_submission.py`의 `TODO V_TABLES` 부분이다.

`validate_tables(clean, summary)` 함수는 정제 데이터 `clean`에서 에이전트별 통계를 다시 계산하고, 제출된 `summary`의 값과 비교한다. 에이전트 한 명의 전체 행은 `part`, 그중 실행 시간이 결측이 아닌 값은 `values`에 들어 있다.

만들어야 하는 `expected` 딕셔너리의 항목은 다음과 같다.

| 키 | 의미 | 계산 기준 |
|---|---|---|
| `runs` | 전체 실행 수 | `part`의 전체 행 수 |
| `measured` | 실행 시간 측정 수 | `values`의 개수 |
| `mean_ms` | 평균 실행 시간 | 결측을 제외한 `values`의 평균 |
| `median_ms` | 중앙값 실행 시간 | 결측을 제외한 `values`의 중앙값 |
| `success_rate` | 성공률 | 전체 `part` 중 `status == "ok"`의 비율 |
| `success_pct` | 성공 백분율 | `success_rate × 100` |

핵심은 지표마다 분모가 다르다는 점이다.

- 실행 시간 평균과 중앙값의 분모는 실행 시간이 측정된 행 수이다.
- 성공률의 분모는 실행 시간 결측 여부와 관계없는 전체 실행 수이다.
- 실행 시간이 하나도 없으면 평균과 중앙값은 `0`이 아니라 `np.nan`이어야 한다.
- 실행 시간 `0`은 결측값이 아니므로 실제 측정값에 포함한다.

## 5. 자동 검증이 확인하는 내용

### 5.1 필수 파일 존재 여부

기본필수 프로젝트에는 적어도 다음 파일이 있어야 한다.

```text
main.py
data/agent_runs.csv
out/clean_runs.csv
out/summary.json
out/charts/latency_by_agent.png
out/charts/latency_hist.png
reports/eda_report.md
```

검사기는 먼저 파일 존재 여부를 확인한다. 필수 파일이 없으면 데이터 내용 검사를 계속하지 않고 누락 목록을 반환한다.

### 5.2 정제 데이터 검사

`out/clean_runs.csv`에는 다음 열이 필요하다.

```text
run_id, agent, latency_ms, tokens, status, day
```

주요 검사 기준은 다음과 같다.

- 정제 데이터가 비어 있지 않아야 한다.
- `run_id`는 결측 없이 고유해야 한다.
- `status`는 `ok` 또는 `error`여야 한다.
- 정제 데이터와 집계 데이터의 에이전트 목록이 같아야 한다.

### 5.3 집계 결과 검사

`out/summary.json`은 에이전트별로 다음 값을 포함해야 한다.

```text
agent, runs, measured, mean_ms, median_ms, success_rate, success_pct
```

검사기는 정제 데이터에서 통계를 다시 계산한 뒤 제출된 집계값과 비교한다. 실수는 표현 과정에서 작은 차이가 생길 수 있으므로 허용 오차를 사용해 비교한다.

### 5.4 PNG 이미지 검사

`out/charts`의 PNG 파일에 대해 다음을 확인한다.

- 이미지 파일을 정상적으로 열 수 있는가?
- 실제 형식이 PNG인가?
- 이미지가 손상되지 않았는가?
- 최소 크기 조건을 만족하는가?

단순히 `.png` 확장자를 붙인 파일은 통과할 수 없다.

### 5.5 보고서와 코드 검사

- `reports/eda_report.md`에 `TODO`나 `[작성]` 표시가 남아 있으면 오류이다.
- `main.py`와 `eda/*.py`에 `raise NotImplementedError`가 남아 있으면 미구현 코드로 판단한다.
- `tests` 폴더가 존재해야 한다.

## 6. 자동 검사와 수동 검토의 차이

자동 검사에서 `automatic_errors`가 빈 목록이어도 최종 제출 승인이 끝난 것은 아니다.

자동 검사는 다음처럼 프로그램으로 판단할 수 있는 항목을 확인한다.

- 필수 파일 존재 여부
- 필수 열과 값의 형식
- ID 고유성
- 집계 계산의 정확성
- PNG 파일의 유효성
- 미작성·미구현 표시 존재 여부

반면 다음 항목은 사람이 직접 검토한다.

- 원본 보존과 정제 정책을 제대로 설명했는가?
- 보고서에 수치 근거 3개, 한계, 개선안이 있는가?
- 그래프의 축, 단위, 표본 수가 적절한가?
- 코드 리뷰와 개인 기여가 구체적인가?
- 실제 Git 커밋이 2개 이상이고 변경 의도가 드러나는가?

따라서 목표는 단순히 자동 오류를 없애는 것이 아니라, 다른 사람이 분석 과정과 결과를 이해하고 재현할 수 있는 제출물을 만드는 것이다.

## 7. 보고서 작성 기준

실습 07 프로젝트의 `reports/eda_report.md`에는 다음 내용이 포함되어야 한다.

1. 분석 질문과 데이터 출처
2. 완전 중복과 ID 충돌을 구분한 정제 정책
3. 수치와 분모가 명시된 근거 3개
4. 각 근거가 연결되는 표 또는 그림 파일
5. 인과로 단정하지 않은 해석
6. 한계와 이를 확인할 추가 데이터 또는 실험
7. 실행 명령, 실제 환경, 실제 테스트 결과
8. 본인이 수정한 내용과 담당 역할
9. 동료 검토 여부와 반영한 수정 사항

이 데이터는 수업용 합성 데이터이므로 실제 서비스의 성능이나 가격을 나타내지 않는다는 점도 명시해야 한다.

## 8. 테스트 자료를 읽는 방법

`data/fixtures`에는 정상 입력뿐 아니라 실패해야 하는 입력도 준비되어 있다.

| 예시 파일 | 확인하려는 상황 |
|---|---|
| `all_missing_latency.csv` | 실행 시간이 전부 결측일 때 평균·중앙값 처리 |
| `conflicting_id.csv` | 같은 ID가 충돌하는 경우 |
| `empty.csv`, `header_only.csv` | 데이터가 비어 있는 경우 |
| `missing_columns.csv` | 필수 열이 누락된 경우 |
| `missing_id.csv` | ID 결측 처리 |
| `unknown_status.csv` | 허용되지 않은 실행 상태 |
| `leading_zero_ids.csv` | ID 앞자리 0을 문자열로 보존하는지 확인 |
| `broken.json`, `nonstandard.json` | 손상되거나 비표준인 JSON 처리 |

테스트는 정상 입력에서 성공하는 것뿐 아니라, 잘못된 입력에서 올바른 오류를 찾는지도 확인해야 한다.

## 9. 정상 완료 시 기대 결과

정상 검증의 핵심 출력 형태는 다음과 같다.

```json
{
  "automatic_errors": [],
  "manual_review": [
    "원본 보존·정제 정책 설명",
    "보고서의 근거 3개·한계·개선안",
    "그림 축·단위·표본 수의 적절성",
    "코드리뷰와 개인 기여",
    "실제 Git 커밋 2개 이상·변경 의도·최종 상태"
  ],
  "notice": "자동 검사 통과는 100점 또는 최종 제출 승인과 동일하지 않습니다."
}
```

`automatic_errors`가 빈 목록이면 프로그램이 확인한 조건에는 문제가 없다는 뜻이다. `manual_review`가 남아 있는 것은 오류가 아니라 강사가 직접 확인할 평가 항목이라는 뜻이다.

## 10. 권장 작업 순서

1. 실습 07 기본필수 프로젝트의 미구현 코드를 완성한다.
2. 실습 07의 `main.py`를 실행해 `out` 결과를 생성한다.
3. 생성된 CSV, JSON, PNG를 직접 열어 확인한다.
4. `reports/eda_report.md`의 모든 임시 문구를 실제 분석 내용으로 교체한다.
5. 실습 08의 `validate_submission.py`에서 `V_TABLES`를 구현한다.
6. 실습 08의 검사 명령을 실행한다.
7. 실패하면 오류 메시지와 fixture의 의도를 기준으로 수정한다.
8. `테스트_기록.md`에 기대값, 실제 결과, 수정 내용을 기록한다.
9. Git 커밋 수와 각 커밋의 변경 의도를 확인한다.
10. 자동 검사 통과 후 수동 검토 항목까지 최종 점검한다.

README에 안내된 대표 명령은 다음과 같다.

```text
python tools/run.py --exercise 08 --level basic
python tools/check.py --exercise 08 --level basic
python tools/check_git.py --project "ex07_project/01_기본필수/day4_eda" --level basic
```

실제 명령은 실습 전체 루트에서 실행하며, 제출 경로는 강사의 현장 안내를 따른다.

## 11. 자주 틀리기 쉬운 부분

- 실습 08 폴더를 새 분석 프로젝트로 착각하지 않는다.
- `expected_outputs`를 제출 결과로 그대로 복사하지 않는다.
- 검사 기준을 통과시키기 위해 `checks.py`나 정답 데이터를 수정하지 않는다.
- 실행 시간 결측값을 임의로 `0`으로 바꾸지 않는다.
- 평균의 분모와 성공률의 분모를 혼동하지 않는다.
- 자동 검사 통과만으로 보고서와 Git 평가까지 끝났다고 생각하지 않는다.
- 보고서 양식의 `[작성]` 문구를 남겨 두지 않는다.
- 테스트를 수행하지 않았다면 수행했다고 쓰지 말고 `미실시`로 기록한다.
